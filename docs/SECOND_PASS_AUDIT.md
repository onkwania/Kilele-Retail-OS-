# Kilele Retail OS — second-pass audit and completion

## Baseline and method

Baseline commit: `1731254`. The working tree was clean. This is an extension/hardening audit, not a rebuild.

The repository inventory covers 87 source/configuration/documentation/test files (841,881 bytes), including all server modules, schema/triggers, client actions/forms/routes, CSS, tests, browser scenarios and deployment files. The API route/permission inventory and client action review were generated from the actual source. Documentation was compared against implementation, not accepted as proof.

**Fresh baseline execution:** `npm ci`, `npm run test`, `npm run typecheck`, `npm run lint`, `npm run build`, `npm run verify`, `npm run db:check`, `npm run test:e2e`, and `npm audit --omit=dev` all exited 0. The existing 55 tests and five browser scenarios passed. The database check passed with 16 audit events. A consistent, private pre-change database backup was taken. Synthetic probes use isolated databases, not the evaluation workspace.

## Existing implementation to preserve

The five-role auth/RBAC system, opaque/CSRF-protected sessions, permanent preview provenance, source-linked/null-price catalogue, versioned price history, integer money, immediate transactional checkout, sale price/tax/COGS snapshots, weighted-average inventory engine, supplier/purchase/expense workflows, reviewed closing, append-only reversals, approval clarification, immutable audit chain, ten reports, durable POS recovery and online backup/restore are substantial working implementations. No replacement POS, authentication, ledger, inventory, approval or reporting architecture is required.

## Current Kenya evidence and limits

KRA states that persons engaged in business must onboard eTIMS and issue electronic tax invoices, while describing applicable small-supplier/buyer-invoicing arrangements [2](https://www.kra.go.ke/services/service/16). KRA's system-to-system route requires development, testing, vetting and certification/self-integration or a verified integrator [5](https://www.kra.go.ke/business/etims-electronic-tax-invoice-management-system/learn-about-etims/etims-system-to-system-integration). Those requirements are not satisfied merely by printing a PIN or calculating VAT.

Safaricom's official [Getting Started guide](https://developer.safaricom.co.ke/apis/GettingStarted) requires sandbox testing, an appropriate M-Pesa account and organisational access for go-live; it describes asynchronous callbacks and current gateway access controls. Kilele currently has no such integration. No credentials, provider confirmation, approval, physical device test or tax certification will be invented.

This is an engineering audit, not a statutory tax opinion or independent penetration-test certification. Final status and closure evidence will be recorded after implementation and fresh verification.

## Final engineering disposition

**Release decision: conditional software acceptance, not an unconditional live-production go-live.** The local single-branch operational workflows are verified. No unresolved P0 was found in the reviewed application paths after remediation. The owned P1 code gaps below were addressed. **External P1 gates E01–E03 remain open**: fiscal acceptance, actual provider confirmation/integration, physical devices and the real deployment/recovery environment.

### What was already complete versus what changed

**Already complete:** server authentication/permissions, transactional sale/stock/journal core, owner-entered nullable prices, historical sale snapshots, independent correction system, supplier/expense/closing flows, append-only audit, basic analytics/reports, baseline POS recovery, private uploads and backup/restore.

**Changed:** the specific controls in the closure table; forward-only schema compatibility; receiving replacements; exact low-value returns and VAT claims; comprehensive financial recovery; receipt identity/layouts; report correctness/coverage; exposed existing dashboard views; barcode preservation; stronger authentication/integrity/backup handling; broad regression and site-acceptance documentation.

### Still not production-ready / external dependencies

1. **E01 — fiscal compliance:** no OSCU/VSCU connector, KRA-issued fiscal identifiers/acknowledgements, certified self-integration or witnessed external eTIMS workflow. Printing a PIN, capturing input VAT or balancing journals does not satisfy this gate. VAT classification/deductibility, fiscal credit notes, invoicing and filing require the owner/accountant and KRA-approved process.
2. **E02 — actual payments:** M-Pesa/card/bank remain manually confirmed records. No live shortcode/acquirer credentials, provider callbacks, statement import/matching or witnessed real settlement/refund has been provided. No provider response or transaction number was invented.
3. **E03 — physical/site acceptance:** no physical scanner/printer/drawer test, actual host/DNS/TLS rollout, configured scheduled/off-site encryption/backup service or witnessed target-host recovery drill. Browser emulation and PDF generation are not hardware certification.
4. **Host/security boundary:** filesystem/database owners remain trusted. The application is not an externally anchored tamper-proof ledger; encrypted storage, protected backup hashes, OS patching, monitoring and independent security review remain deployment responsibilities. Uploaded files are not malware-scanned.
5. **Operational limits:** single-process/local-SQLite deployment; whole stock units; no offline posting, customer credit ledger, multi-site transfer/HA workflow or autonomous financial AI. Opening drawer counts are counts, not repeated cash-capital journal injections; the journal reports recorded operations, not a complete statutory opening balance sheet.

### Required manual setup and activation

Use a clean operational database, supported Node 22/24, private HTTPS ingress and owner-only storage. Enter the actual business PIN/address/branch, genuine supplier records, physical packages/barcodes, owner prices and tax treatment. Record witnessed opening stock/float. Use individual accounts and genuinely separate reviewers. Resolve outstanding submissions before branch/role reassignment. Configure backup retention, encrypted off-site copying, restore drills and alerting. Complete [hardware/site acceptance](HARDWARE_ACCEPTANCE.md) and the deployment checklist. For future branches, follow [MULTI_BRANCH_READINESS.md](MULTI_BRANCH_READINESS.md); no single-branch workflow was unnecessarily rebuilt.
